# [项目名称] Bug 登记簿

## 1. 文档作用

这份文档用于统一记录项目中的 **Bug**，确保所有已发现的问题都具备：
- 唯一标识
- 明确状态
- 清晰影响范围
- 可追踪处理过程
- 可验证最终结果

它的目标不是“把问题记下来就算完”，而是让每一个 Bug 都至少处于某种**明确状态**，避免出现：
- 发现了但没记
- 记了但没人跟
- 修了但没验证
- 旧 Bug 散落在聊天记录里找不到
- 同一个 Bug 被重复提报和重复处理

---

## 2. 使用原则

### 原则 1：只要是已发现的实现错误，就应该进 Bug Register
包括但不限于：
- 前端展示异常
- 后端接口错误
- JSON 结构不一致
- 规则引擎判断错误
- Overlay 渲染异常
- 上传失败
- 状态流转异常
- 性能异常（如明显超时、死循环、阻塞）

### 原则 2：一个 Bug 可以未解决，但不能无状态
至少必须标记为：
- `new`
- `confirmed`
- `in_progress`
- `fixed`
- `verified`
- `deferred`
- `wont_fix`

### 原则 3：Bug 和技术问题分开管理
- **Bug**：系统行为与预期不符，已经出现错误
- **Tech Question**：技术路线不确定、方案待定，不一定已经是错误

### 原则 4：描述 Bug 时要尽量可复现
不能只写“这里有问题”，必须尽量补充：
- 发生位置
- 触发条件
- 实际表现
- 预期表现
- 复现步骤

### 原则 5：修复完成不等于关闭
只有经过验证，才能从 `fixed` 进入 `verified`。

## 3. Bug 状态流转规范

### 状态枚举
- `new`
- `confirmed`
- `in_progress`
- `fixed`
- `verified`
- `deferred`
- `wont_fix`
- `duplicate`
- `obsolete`
- `reopened`

### 推荐流转路径
```text
new -> confirmed -> in_progress -> fixed -> verified
```

## 8. Bug 去重规则

### 属于同一个 Bug 的情况
- 相同根因
- 相同触发逻辑
- 只是不同页面暴露同一问题

### 应新开 Bug 的情况
- 根因不同
- 修复路径不同
- 影响模块不同
- 需要独立跟踪处理

---

## 9. Bug 关闭规则

一个 Bug 只有在满足以下条件后，才建议进入 `verified`：

1. 问题已被修复
2. 已按预定方式验证
3. 未再复现
4. 如涉及前后端联动，联调通过
5. 相关文档或说明已更新（如有必要）
