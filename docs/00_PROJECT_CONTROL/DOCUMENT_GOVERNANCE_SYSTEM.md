# 文档治理规则

## 目的

让不同 AI、不同会话和不同执行工具能继续同一个项目，减少目标偏移、重复操作和未经验证的完成声明。文档是否有用，以这些结果衡量。

## 信息归属

| 信息 | 放在哪里 | 更新方式 |
|---|---|---|
| 稳定的项目规则、读取顺序 | AGENTS.md / 映射的 rules | 有规则变化才修改，入口保持短 |
| 用户确认的目标与验收条件 | 当前产品合同或最小任务说明 | 记录来源；变化时标明影响 |
| 当前阶段、已知事实、假设、下一步 | 映射的 status | 原位维护当前结论，事实链接到证据 |
| 未完成现场、恢复命令、临时限制 | 映射的 handoff | 完成即移除现场，历史另存 |
| 为什么作出选择、何时重新考虑 | 映射的 decisions | 追加决定与替代关系 |
| 一次委派的生命周期 | tasks_dir 中对应任务 | 一个任务一份状态，其他入口只链接 |
| 某版本实际运行、验证结果 | evidence_dir 或已有证据目录 | 留存原始记录，不倒改历史为通过 |
| 文档索引、上下文简报 | index / brief | 引用上面的权威来源，不另建进度副本 |

`project-os.json` 记录实际映射，已有项目不必改名或搬目录。映射只是导航与检查配置，不赋予外部执行权限。

## 三种信息与一个结论

- **要求**：用户已确认要实现什么。模型不能悄悄改变成功标准来让自己通过。
- **假设**：尚未验证的选择，写清如何验证和什么结果会推翻它。
- **观察**：在什么版本、环境、输入下，实际发生了什么，证据在哪里。
- **验收**：依据哪些要求和观察作出的判断。未覆盖的部分保持未验证。

“已实现”“某项检查通过”“服务已加载”“用户认可效果”分别表达。进程退出成功或 JSON 合法不能单独证明业务完成。历史测试通过也不能自动证明当前变更通过。

## 冲突处理

规则来源遵守宿主约束与用户当前要求。项目规范描述意图，代码和运行证据描述观察；两者不符是待解决的差异，不能以其中一个代替另一个。

先核对来源、时间、版本与适用范围，再修正唯一当前结论。历史记录保留，并注明被哪个新结论替代。不要在规则开头不断叠加“以下旧说明全部覆盖”的进度段落。

## 最小维护

每轮实质工作结束，AI 更新发生变化的权威来源，并给出一句结果、验证依据与未覆盖事项。小改动不强制新增 PRD、决策日志和长篇会话总结。一个字段只维护一处。

关键验证记录至少包含：目标、代码 revision（无 Git 时记录具体文件及 hash）、检查命令或观察方式、结果、原始证据、未覆盖范围。对未提交改动，注明 dirty 状态和可重现 diff / 文件 hash，不把结果归给一个不包含改动的提交。

## 接入、协作与验证

- [接入指南](../03_DELIVERY/DELIVERY_PROJECT_INSTANTIATION_GUIDE_v1.md)：源工具包与目标项目的边界、已有文档映射、升级。
- [Harness 合同](../02_TECH/HARNESS_CONTRACT.md)：派工、交付、验收和恢复。
- [治理试验](../03_DELIVERY/GOVERNANCE_TRIAL.md)：让 AI 自己演练，用结果证明是否可接续。

自动检查能发现结构与声明之间的部分矛盾，不能证明文档里每句话都真实。没有进行的行为试验要显示“未验证”。
